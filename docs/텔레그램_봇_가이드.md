# 텔레그램 봇 가이드

업데이트 기준: 2026-06-02

대화탭과 텔레그램 봇은 같은 명령 계층(`CommandService`)을 공유한다. 이 문서는 텔레그램 봇에서 자주 쓰는 슬래시 명령, 자연어 흐름, 첨부 처리, inline keyboard, 모바일 handoff 작동 방식을 정리한다.

## 1. 메시지 흐름 한눈에 보기

```
사용자 입력
  ├─ 음성 → 자동 STT (transcript echo)
  ├─ 사진 → Vision 분석
  ├─ 문서/파일 → 모델이 직접 참조
  └─ 텍스트 → 슬래시 명령 / 자연어 / 스킬 별명 자동 라우팅
       │
       ▼
응답 생성
  ├─ 본문 (Markdown→Telegram 안전 변환, 코드펜스 보존 chunking)
  ├─ 본문 길이 9000자 ↑ 또는 청크 5개 ↑ → .txt 첨부 자동 전환
  ├─ 대형 코딩 결과 / diff / 로그 / 파일 / task output / doctor JSON → 모바일 요약 + handoff
  └─ footer: — provider·model · 🎯 활성 스킬 · ⏱ 소요시간
       │
       ▼
inline keyboard (해당하는 명령 응답에 한해 자동 부착)
  /skill status → [🚫 끄기] [📋 목록]
  /think status / /web status → [✅ 켜기] / [🚫 끄기]
  /llm status → [Groq] [Gemini] [Cerebras] [NVIDIA] [Copilot]
  /coding files → [⬇️ 1] [⬇️ 2] [⬇️ 3]
```

## 2. 슬래시 명령

### 스킬

| 명령 | 동작 | 예시 |
|---|---|---|
| `/skill list` | 등록된 스킬 목록 | — |
| `/skill use <이름> [project|global]` | 스킬 활성화 | `/skill use eli5` |
| `/skill status` | 현재 활성 스킬 + 끄기 버튼 | — |
| `/skill off` (= `/off`) | 활성 스킬 해제 | — |
| `/skill get <이름>` | 스킬 본문 미리보기 | `/skill get casual-empathy` |
| `/skill create <이름> [scope]` | 새 스킬 등록 (본문은 다음 줄부터) | 아래 참고 |
| `/skill quick <별명> <스킬>` | 단축 별명 등록 | `/skill quick e eli5` |
| `/skill quick list` | 등록된 별명 목록 | — |
| `/skill quick remove <별명>` | 별명 제거 | `/skill quick remove e` |
| `/<별명> [질문]` | 별명으로 즉시 호출 | `/e 디지털 카메라 원리 알려줘` |

별명 등록 후 `/<별명> 질문`을 입력하면 내부적으로 `<스킬> 스킬 사용해서 <질문>` 자연어로 rewrite된다.

## 4. 첨부 파일

| 첨부 | 동작 |
|---|---|
| 🎙️ 음성 | `SttBaseUrl/SttModel/SttApiKey` 설정 시 자동 전사 → "🎙️ 들은 내용: …" echo → LLM 처리 |
| 🖼️ 사진 | Vision 모델로 이미지 분석 (캡션 없으면 자동 안내) |
| 📎 문서/PDF/코드 | 모델이 본문을 직접 참조해 요약·분석 |

음성 transcript echo는 잘못 들렸을 때 사용자가 즉시 인지하고 다시 말할 수 있게 해 준다.

## 5. Inline keyboard (callback_query)

`/skill status`, `/think status`, `/web status`, `/llm status`, `/coding files` 같은 명령은 응답 하단에 작은 버튼 행이 자동 부착된다. 버튼을 누르면 그 자리에서 즉시 다음 명령이 실행된다 (별도 입력 없음).

내부 동작:
- 봇이 `getUpdates`에 `allowed_updates=[message, callback_query]`를 명시
- 버튼 tap → `callback_query` 수신 → `answerCallbackQuery`로 spinner 제거 → `callback_data`를 새 사용자 입력처럼 ExecuteAsync로 흘려보냄

핸들러는 응답 끝에 `__TG_BUTTONS__` 마커로 버튼 행을 첨부하고, `TelegramUpdateLoop`가 마커를 파싱해 `reply_markup`으로 변환한다.

## 6. 모바일 handoff 운영 기준

텔레그램은 알림과 트리거에 가깝게 쓴다. 긴 코딩 결과, 대형 diff, 로그, 파일 본문, task output, doctor JSON처럼 모바일에서 읽기 어려운 출력은 본문 전체를 풀지 않는다.

대신 텔레그램에는 다음 내용만 표시한다.

- 짧은 요약과 앞부분 프리뷰
- 대상 파일, graph/task id, doctor 범위 같은 식별자
- 다음에 보낼 명령: `/coding files`, `/coding download <번호>`, `/task status`, `/task output`, `/handoff`
- handoff marker: `telegram_command_output_handoff` 또는 `telegram_heavy_output_handoff`

명령별 기준:

| 경로 | 모바일 처리 |
|---|---|
| 대형 코딩 결과 | 요약 후 `/coding files`, `/coding download <번호>`, `/handoff` 안내 |
| `/coding file <번호|경로>` 대형 파일 | 짧은 프리뷰만 표시, 전체는 `/coding download` 또는 데스크톱에서 확인 |
| `/refactor preview` 대형 diff | diff 전체를 직접 출력하지 않고 요약+handoff |
| `/task output` 대형 stdout/stderr/result | task id와 짧은 프리뷰, `/task status`와 `/handoff` 안내 |
| `/doctor json` 대형 JSON | JSON 전체 대신 요약+handoff |
| `/handoff [project-key]` | `~/.omnux/notebooks/<project-key>/handoff.md`를 만들고 데스크톱 Notebooks 화면의 Handoff 패널로 안내 |

`/coding download <번호|경로>`의 로컬 정책 검증 범위:

- `TelegramCodingDownloadPolicy`와 `TelegramCodingDownloadPolicyTests`가 다운로드 대상을 변경 파일 목록 기반으로만 고른다.
- 1부터 시작하는 번호 선택과 변경 파일의 상대 경로 선택을 허용한다.
- 목록 밖 경로 거부: 변경 파일 목록 밖 임의 경로는 거부한다.
- `/tmp/run`과 `/tmp/run2` 같은 sibling prefix를 같은 실행 디렉터리로 오인하지 않는다.
- 첨부 파일명은 안전한 파일명으로 정리하고, 파일명이 없으면 fallback 이름을 만든다.
- 텔레그램 문서 첨부 상한은 8MB로 고정한다.
- `TelegramClientTests`가 실제 Telegram 서버 없이 fake HTTP로 `sendDocument` multipart 요청의 endpoint, `chat_id`, caption, document 본문, 파일명을 확인한다.
- Telegram token/chat id가 없으면 `sendDocument` 요청 자체가 나가지 않는지 확인한다.

Deep link 최종 판단: 지금은 별도 데스크톱 deep link 프로토콜을 도입하지 않는다. `/handoff` 응답은 `omnux://` 링크를 만들지 않고, 로컬 `handoff.md` 경로와 데스크톱 Notebooks/Handoff 화면 안내를 보여준다. Phase 5에서 데스크톱 라우팅과 앱 프로토콜이 확정되면 그때 deep link를 별도 작업으로 재검토한다.

## 7. 실제 모바일 QA 체크리스트

실제 봇 토큰, chat id, 허용 user id, 모바일 텔레그램 클라이언트가 있어야 완료 처리할 수 있다. 로컬 단위 테스트와 계약 검사는 정책 회귀만 확인한다.

운영 중인 미들웨어 Telegram polling 루프를 잠시 멈춘 뒤 다음 live QA를 실행한다. 이 명령은 토큰 값을 출력하지 않고 `OMNUX_TELEGRAM_BOT_TOKEN`/`OMNUX_TELEGRAM_CHAT_ID`, `*_FILE`, 기본 macOS Keychain 항목을 순서대로 사용한다.

```bash
node scripts/telegram-mobile-live-qa.mjs --timeout-sec 180
```

완료 판정은 다음 4개 값이 모두 `true`일 때만 통과한다.

- `outboundMessageOk`: 실제 Telegram `sendMessage` 성공
- `outboundDocumentOk`: 실제 Telegram `sendDocument` 성공
- `inboundTextAckOk`: 모바일에서 `/omniqa-ok <QA-ID>` 응답 수신
- `inboundDocumentEchoOk`: 모바일에서 받은 `.txt` 첨부를 다시 업로드했고, echo-back 문서 본문에서 같은 `QA-ID` 확인

수동 확인 항목:

1. 모바일에서 `/help handoff` 또는 `/handoff`를 보내면 데스크톱 Handoff 안내와 로컬 `handoff.md` 경로가 보이는지 확인한다.
2. 대형 코딩 결과가 텔레그램 본문 전체로 풀리지 않고 `/coding files`, `/coding download <번호>`, `/handoff` 안내로 좁혀지는지 확인한다.
3. `/coding download <번호>`가 실제 파일 첨부로 내려오는지 확인한다. live QA는 `sendDocument` 성공과 모바일 echo-back 본문 `QA-ID`로 실제 첨부 수신을 판정한다.
4. `/refactor preview`, `/task output`, `/doctor json`의 큰 출력이 `telegram_command_output_handoff` marker와 함께 짧은 프리뷰만 표시하는지 확인한다.
5. deep link가 없다는 현재 정책을 확인한다. 텔레그램 응답에 `omnux://` 링크가 없어야 하며, 사용자가 직접 데스크톱 앱의 Notebooks/Handoff 화면을 열 수 있어야 한다.

## 8. 다중 user allowlist

기본은 `OMNUX_TELEGRAM_CHAT_ID`로 지정한 단일 chat만 처리한다. 여러 사용자에게 봇을 열려면 `OMNUX_TELEGRAM_ALLOWED_USER_ID`에 user_id를 콤마/세미콜론/공백으로 나열하면 된다.

```bash
export OMNUX_TELEGRAM_ALLOWED_USER_ID="123456789,234567890,345678901"
```

비허용 호출은 stderr에 한 줄 로그(`reason=user_id_not_in_allowlist chat=… from=… text=…`)만 남기고 응답은 보내지 않는다.

## 9. 응답 footer

매 응답 본문 하단에 한 줄 footer가 붙는다.

```
— gemini·flash · 🎯 eli5 · ⏱ 4.7s
```

- provider·model: 어떤 모델이 답했는지 즉시 확인
- 🎯 활성 스킬: 표시되면 그 스킬이 적용된 응답
- ⏱ 소요시간: turn 시작부터 응답 완료까지 (1초 미만은 표시 안 함)

## 10. 끊긴 응답 표시

스트림이 timeout/quota/오류로 도중에 끊기면 본문 끝에 다음 라인이 자동 추가된다.

```
⚠️ [provider 응답이 도중에 끊겼습니다 — timeout. 다시 시도해 주세요.]
```

부분 응답 자체는 그대로 보여 주되, 사용자는 즉시 잘렸다는 사실을 인지한다.

## 11. 다중 스킬 거부

한 메시지에 스킬 이름이 2개 이상 등장하면 다음과 같이 거부된다.

```
한 번에 한 개의 스킬만 사용할 수 있어요.
지금 입력에서 스킬 이름이 2개 발견됐습니다: `eli5`, `casual-chat`
사용할 스킬 하나만 남기고 다시 보내 주세요.
```

스킬 이름 매칭은 단어 경계 기반이라 "ai" 같은 짧은 스킬 이름이 일반 영단어("aim") 안에 묻혀 잘못 매칭되지 않는다.

## 12. 활성 스킬 영구화

`/skill use eli5` 또는 자연어로 활성화한 스킬은 `ConversationThread.ActiveSkillName`으로 디스크에 저장된다. 미들웨어를 재시작해도 마지막 활성 스킬이 자동 복원되어 다음 메시지부터 그대로 적용된다.

활성 스킬이 있는 상태에서 URL이나 웹검색이 필요한 질문을 보내도 빠른 웹 응답 경로가 스킬 지침을 우회하지 않는다. 웹 문맥은 공통 입력 준비 단계에 붙고, 응답 형식과 말투는 활성 스킬을 따른다.

`/skill create`는 기존 스킬을 자동 덮어쓰지 않는다. 같은 이름이 있으면 저장 실패 메시지를 반환하므로, 기존 스킬 수정은 스킬탭에서 진행한다.
