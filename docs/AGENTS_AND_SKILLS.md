# AGENTS / 스킬 / 명령

[한국어](./AGENTS_AND_SKILLS.md) · [English](./en/agents-and-skills.md)

업데이트 기준: 2026-09-12

omnux는 프로젝트 지침과 스킬을 런타임 문맥으로 읽는다. 항상 주입할 지침은 AGENTS에 두고 필요할 때만 켤 작업 방식은 Skill로 뺀다.

스킬은 데스크톱 앱과 텔레그램 봇에서 같게 동작한다. 대화 입력창의 스킬 배지나 슬래시 명령으로 켜고 끈다.

## 읽는 순서

1. `~/.omnux/AGENTS.md`
2. 프로젝트 루트와 현재 작업 디렉터리 사이의 `AGENTS.override.md`, `AGENTS.md`
3. fallback 문서: 기본 `TEAM_GUIDE.md`, `.agents.md` (`OMNUX_PROJECT_CONTEXT_FALLBACK_FILENAMES`로 바꾼다)
4. 프로젝트 skill: `.omni/skills/**/SKILL.md`
5. 전역 skill: `~/.omnux/skills/**/SKILL.md`
6. 프로젝트 command: `.omni/commands/*.md`
7. 전역 command: `~/.omnux/commands/*.md`

## 스킬 동작

- 스킬 파일은 기본으로 모든 요청에 주입되지 않는다.
- 사용자가 스킬 이름을 말하거나 스킬 사용을 요청하면 활성화된다.
- 활성 스킬은 같은 스레드에서 유지되고 `ConversationThread.ActiveSkillName`으로 디스크에 저장된다. 미들웨어를 재시작해도 마지막 활성 스킬이 복원된다.
- `스킬 중지`, `일반 대화로 돌아가`, `/skill off`, `/off`로 해제한다.
- 질문·빌드 입력창의 스킬 배지를 끄면 UI 선택과 서버에 저장된 sticky 스킬이 함께 풀린다.
- 질문 화면과 텔레그램 봇은 같은 감지·활성화·해제 흐름을 쓴다.
- 스킬 이름 매칭은 단어 경계 기반이다. `ai`, `doc` 같은 짧은 이름이 일반 영단어 안에 묻혀 잘못 걸리지 않는다.
- 활성 스킬이 있으면 URL·웹검색 빠른 응답 경로도 공통 입력 준비 경로를 지난다.
- 같은 이름의 프로젝트 스킬과 전역 스킬이 있으면 프로젝트 스킬을 우선한다.

### 다중 스킬 거부

한 입력에서 스킬 이름이 2개 이상 발견되면 즉시 거부한다.

```text
한 번에 한 개의 스킬만 사용할 수 있어요.
지금 입력에서 스킬 이름이 2개 발견됐습니다: `eli5`, `casual-chat`
사용할 스킬 하나만 남기고 다시 보내 주세요.
```

질문, 빌드, 텔레그램 모두 같다.

### 단일 스킬 자동 교체

이미 활성화된 스킬이 있을 때 다른 스킬을 언급하면 이전 스킬이 끝나고 새 스킬만 적용된다. LLM 입력에 `[Skill Switched: 이전 → 새]` 알림이 함께 전달되어 모델이 이전 스킬의 톤과 규칙을 이어 쓰지 않는다.

### UI 드롭다운과 프롬프트가 다를 때

UI 드롭다운에서 고른 스킬과 프롬프트에 적은 스킬이 다르면 프롬프트에 적은 스킬을 적용한다. 사용자가 직접 입력한 의도를 더 우선한다.

UI 드롭다운 선택은 서버에도 해당 대화의 활성 스킬로 반영된다. 배지의 끄기 버튼을 누르면 서버 sticky 상태도 함께 풀린다.

### 스킬과 Think+ 동시 사용

추론 모드(Think+)와 스킬을 같이 켤 수 있다. 활성 스킬이 있으면 Think+ 컨텍스트의 8번 톤 규칙(`결론 먼저, 군더더기 없이`)이 "출력 형식·말투는 활성 스킬 지침을 따르고, Think+ 자료는 사실 근거로만 사용"으로 바뀌어 톤이 충돌하지 않는다. 사실 정확성 규칙 1~7은 그대로다.

## 자주 쓰는 슬래시 명령

텔레그램과 질문 화면에서 같이 쓴다.

| 명령 | 동작 |
|---|---|
| `/skill list` | 등록된 스킬 목록 |
| `/skill status` | 현재 활성 스킬과 `[🚫 끄기]` `[📋 목록]` inline 버튼 |
| `/skill use <name>` | 스킬 활성화 |
| `/skill off` (= `/off`) | 활성 스킬 해제 |
| `/skill quick <별명> <스킬>` | 단축 별명 등록 (`/skill quick e eli5`) |
| `/skill quick list` | 등록된 별명 목록 |
| `/skill quick remove <별명>` | 별명 제거 |
| `/<별명> [질문]` | 별명으로 즉시 호출 (`/e 양자역학 원리`) |

별명은 `~/.omnux/skill_aliases.json`에 저장된다.

`/skill create`는 같은 이름의 기존 스킬을 조용히 덮어쓰지 않는다. 기존 스킬을 고치려면 데스크톱 **도구** 화면에서 열어 저장한다.

## 대화 중 스킬 자동 생성

대화나 텔레그램에서 "스킬 만들어줘", "이런 스킬 등록해줘"라고 하면 미들웨어가 응답 본문에 `<omni:skill>` 디렉티브를 출력한다. 이 디렉티브는 응답 후처리에서 파싱되어 `.omni/skills/<name>/SKILL.md` 파일을 만든다.

```xml
<omni:skill name="kebab-case-name" description="한 줄 설명" scope="project" overwrite="false">
스킬 본문(markdown)
</omni:skill>
```

| 속성 | 규칙 |
|---|---|
| `name` | 소문자·숫자·`-`만 쓴다. 한글, 공백, 언더스코어는 안 된다 |
| `description` | 언제 이 스킬을 쓰는지 한 줄로. 미들웨어가 호출 판단에 쓴다 |
| `scope` | 기본 `project`. "전역"이나 "global"을 명시하면 `global` |
| `overwrite` | 기본 `false`. 사용자가 명시로 동의했을 때만 `true` |

본문은 반복 사용할 실행 지침으로 8줄 이상 쓰고 목표·사용 흐름·응답 원칙·출력 형식·확인 기준·피해야 할 것을 담는다.

## 좋은 SKILL.md 기준

`description`은 스킬 호출 판단에 쓰이므로, 무엇을 하는지와 어떤 요청에서 써야 하는지를 한 줄에 구체적으로 적는다.

본문은 보통 이 구조를 따른다.

| 절 | 내용 |
|---|---|
| 목표 | 스킬이 해결할 일 |
| 사용 흐름 | 입력 확인, 처리 순서, 되물을 조건 |
| 응답 원칙 | 말투, 깊이, 근거 수준, 예외 처리 |
| 출력 형식 | 답변 구조, 표·목록·코드 사용 기준 |
| 확인 기준 | 답변 전 점검할 품질 기준 |
| 피해야 할 것 | 추측, 과장, 원치 않는 조언, 장황한 설명 |

대화·톤 스킬도 3~5줄로 끝내면 안 된다. 첫 문장 방식, 답변 길이, 조언을 줄 조건, 피할 표현까지 적어야 실제 대화에서 일관되게 동작한다. 코드·리뷰 스킬은 읽을 자료, 변경 원칙, 검증, 위험 보고 기준을 담는다. 검색·리서치 스킬은 우선 출처, 최신성 확인, 인용 방식, 불확실성 표기 기준을 담는다.

## 배치 예시

```text
.omni/
  skills/ui-review/SKILL.md
  commands/release-check.md
```

스킬에는 반복되는 답변 방식, 리뷰 기준, 설명 톤을 담는다. 명령 템플릿은 릴리스 점검처럼 매번 같은 구조로 실행하는 작업에 맞다.

저장소에는 `.omni/skills/` 아래에 예시 스킬 10개가 들어 있다. `brainstorming`, `casual-chat`, `casual-empathy`, `code-review`, `coding-for-beginners`, `eli5`, `explain-optical-design`, `refactor`, `skill-creator`, `write-tests`다.
